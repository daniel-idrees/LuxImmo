# Skill Router — Start Here

**Read this file first, before applying any other skill in `ai/Skill/`.**

The skills in this folder describe several interchangeable choices — whether to centralize build configuration, whether to split the app into many modules or keep one, whether to write performance and unit tests, and which test-doubling style to use. Picking one path and sticking to it keeps the codebase consistent. This router asks for those choices once, remembers them, and then tells you which skills apply.

## Workflow

Follow these steps in order at the start of any task that will touch the `ai/Skill` skills.

### Step 1 — Load saved preferences if they exist

Check for `ai/Skill/.preferences.md`.

- **If it exists:** read it, briefly restate the chosen preferences to the user (one line), and skip straight to [Step 4 — Route](#step-4--route). Do **not** re-ask the questions. Re-run the interview (Step 2) only if the user explicitly asks to change or reconfigure their preferences.
- **If it does not exist:** continue to Step 2.

### Step 2 — Run the preferences interview

Ask the user the following questions. Present the **recommended default** for each so they can accept quickly, but let them choose. Keep it to one short round of questions.

1. **Build logic** — Prefer centralized build logic (Gradle convention plugins + a single version catalog), or keep build configuration inline?
   - *Recommended: Yes, use centralized build logic.* It keeps each module's `build.gradle.kts` tiny and shared config in one place. A version catalog is worth it on any project; convention plugins pay off most on multi-module projects.

2. **Module structure** — Single module (packages inside one Gradle module) or multi module (`:core:*` / `:feature:*` with build-enforced boundaries)?
   - *Recommended: Multi module for an app expected to grow; single module for a small app, prototype, or sample.*

3. **Performance testing** — Set up performance testing (a Macrobenchmark module measuring startup + Baseline Profiles)?
   - *Recommended: Yes for a production app; optional for a prototype or sample.*

4. **Unit testing** — Write JVM unit tests?
   - *Recommended: Yes.*
   - **If yes → test-doubling style:** fakes or mocks?
     - *Recommended: Fakes* (the preferred default here). Reach for **mocks** only when a test must verify interactions or stub a collaborator where a hand-written fake is overkill. You may pick "fakes as default, mocks when needed."

> Optional follow-up (only if unit testing = yes): also set up **on-device Compose UI / screen tests**? This is separate from JVM unit testing and governed by `compose-ui-testing`. Recommended: yes when the app has screens worth asserting on.

### Step 3 — Save the answers

Write the chosen answers to `ai/.preferences.md` using this template, then tell the user it's saved and will be reused next time:

```markdown
---
# ai/references — generated by skill-router. Edit or delete to reconfigure.
build_logic: yes | no
module_structure: multi-module | single-module
performance_testing: yes | no
unit_testing: yes | no
unit_testing_style: fakes | mocks | fakes-default-mocks-when-needed | n/a
compose_ui_testing: yes | no
decided_on: <YYYY-MM-DD>
---

Notes: <anything the user clarified, e.g. "single module for now, will split later">
```

### Step 4 — Route

Apply the **core skills** always, plus the **conditional skills** selected by the saved preferences. Skip the ones that don't match.

#### Core skills (always apply)

| Skill (`name`) | Path |
| --- | --- |
| `architecture-layers` | `architecture-layers/SKILL.md` |
| `compose-ui` | `compose-ui/SKILL.md` |
| `compose-navigation-3` | `compose-navigation-3/SKILL.md` |
| `hilt-dependency-injection` | `hilt-dependency-injection/SKILL.md` |

#### Conditional skills (apply only when the preference matches)

| Preference | Value | Skill to apply | Path |
| --- | --- | --- | --- |
| `build_logic` | `yes` | `build-logic` | `build-logic/SKILL.md` |
| `build_logic` | `no` | *(none — keep build config inline)* | — |
| `module_structure` | `multi-module` | `multi-module-structure` | `module-structure/multi-module/SKILL.md` |
| `module_structure` | `single-module` | `single-module-structure` | `module-structure/single-module/SKILL.md` |
| `performance_testing` | `yes` | `performance-testing` | `performance-testing/SKILL.md` |
| `unit_testing` | `yes` + `fakes` | `unit-testing-with-fakes` | `unit-testing/with-fakes/SKILL.md` |
| `unit_testing` | `yes` + `mocks` | `unit-testing-with-mocks` | `unit-testing/with-mocks/SKILL.md` |
| `compose_ui_testing` | `yes` | `compose-ui-testing` | `compose-ui-testing/SKILL.md` |

> When the style is "fakes as default, mocks when needed," treat `unit-testing-with-fakes` as the primary skill and consult `unit-testing-with-mocks` only for interaction-verification tests.

Only the skills selected above should guide the work. If a task clearly calls for a skill the preferences excluded (for example, the user asks for a benchmark but `performance_testing` is `no`), point out the mismatch and offer to update `ai/.preferences.md` rather than silently switching.
