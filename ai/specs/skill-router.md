# Skill Router — Start Here

**Read this file first, before applying any other skill in `ai/Skill/`.**

The skills in this folder describe several interchangeable choices — whether to centralize build configuration, whether to split the app into many modules or keep one, whether to persist data locally for offline-first access, whether to write performance and unit tests, and which test-doubling style to use. Picking one path and sticking to it keeps the codebase consistent. This router asks for those choices once, remembers them, and then tells you which skills apply.

## Workflow

Follow these steps in order at the start of any task that will touch the `ai/Skill` skills.

### Step 1 — Load saved preferences if they exist

Check for `ai/.preferences.md`.

- **If it exists:** read it, briefly restate the chosen preferences to the user (one line), and skip straight to [Step 4 — Route](#step-4--route). Do **not** re-ask the questions. Re-run the interview (Step 2) only if the user explicitly asks to change or reconfigure their preferences.
- **If it does not exist:** continue to Step 2.

### Step 2 — Run the preferences interview

Ask the user the following questions. Present the **recommended default** for each so they can accept quickly, but let them choose. Keep it to one short round of questions.

1. **Build logic** — Prefer centralized build logic (Gradle convention plugins + a single version catalog), or keep build configuration inline?
   - *Recommended: Yes, use centralized build logic.* It keeps each module's `build.gradle.kts` tiny and shared config in one place. A version catalog is worth it on any project; convention plugins pay off most on multi-module projects.

2. **Module structure** — Single module (packages inside one Gradle module) or multi module (`:core:*` / `:feature:*` with build-enforced boundaries)?
   - *Recommended: Multi module for an app expected to grow; single module for a small app, prototype, or sample.*

3. **Offline-first storage** — Persist data locally (Room) and treat the local cache as the single source of truth, so the app works without a connection? Or fetch straight from the network with no local persistence?
   - *Recommended: Yes (offline-first) for a production app that should keep working offline.* Choose **no** for a prototype, sample, or an app whose data is always live/online — this skips the `:core:database` (Room) layer entirely and uses a simpler network-only repository.

4. **Performance testing** — Set up performance testing (a Macrobenchmark module measuring startup + Baseline Profiles)?
   - *Recommended: Yes for a production app; optional for a prototype or sample.*

5. **Unit testing** — Write JVM unit tests?
   - *Recommended: Yes.*
   - **If yes → test-doubling style:** fakes or mocks?
     - *Recommended: Fakes* (the preferred default here). Reach for **mocks** only when a test must verify interactions or stub a collaborator where a hand-written fake is overkill. You may pick "fakes as default, mocks when needed."

> Optional follow-up (only if unit testing = yes): also set up **on-device Compose UI / screen tests**? This is separate from JVM unit testing and governed by `compose-ui-testing`. Recommended: yes when the app has screens worth asserting on.

### Step 3 — Save the answers

Write the chosen answers to `ai/.preferences.md` using this template, then tell the user it's saved and will be reused next time:

```markdown
---
# ai/references — generated by skill-router. Edit or delete to reconfigure.
build_logic: yes | no
module_structure: multi-module | single-module
offline_first: yes | no
performance_testing: yes | no
unit_testing: yes | no
unit_testing_style: fakes | mocks | fakes-default-mocks-when-needed | n/a
compose_ui_testing: yes | no
decided_on: <YYYY-MM-DD>
---

Notes: <anything the user clarified, e.g. "single module for now, will split later">
```

### Step 4 — Route

Apply the **core skills** always, plus the **conditional skills** selected by the saved preferences. Skip the ones that don't match.

#### Module-structure toggle (changes how `architecture-layers` is applied)

`module_structure` does not select a separate skill — like `offline_first`, it changes how the always-on `architecture-layers` skill lays out the code. The full module/package breakdown and the exact dependency rules for both options live in `architecture-layers/references/modularization.md`.

- **`module_structure: multi-module`** — split the app into many small Gradle modules, by layer (`:core:*`) and by feature (`:feature:*`); the build system enforces the dependency boundaries.
- **`module_structure: single-module`** — organize the same layers as **packages inside one Gradle module**; boundaries are kept by convention (optionally a lint / Konsist rule) rather than by the build graph.

#### Offline-first toggle (changes how `architecture-layers` is applied)

`offline_first` does not select a separate skill — it changes how the always-on `architecture-layers` skill and the module/package layout are built:

- **`offline_first: yes`** — apply `architecture-layers` in full: the `:core:database` (Room) layer (§4.4), the offline-first repository (§4.2), and entity mappers. Reads flow out of the database as the single source of truth; the network only refreshes the cache. This is the default the skill examples assume.
- **`offline_first: no`** — apply the **network-only variant** of `architecture-layers` (see its `references/details.md` → *Network-only (no offline-first) variant*). **Skip the `:core:database` module / `data/database/` package, Room, DAOs, entities, the Room convention plugin, and the entity mappers entirely.** The repository depends only on the network data source, maps DTO → domain directly, and returns the domain `Result` from one-shot reads (no caching, no `refresh()` split). In a multi-module project, also drop `:core:data`'s dependency on `:core:database`.

> If a task asks for local persistence/caching but `offline_first` is `no` (or the reverse), point out the mismatch and offer to update `.preferences.md` rather than silently switching.

Only the skills selected above should guide the work. If a task clearly calls for a skill the preferences excluded (for example, the user asks for a benchmark but `performance_testing` is `no`), point out the mismatch and offer to update `ai/.preferences.md` rather than silently switching.
